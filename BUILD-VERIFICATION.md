After restarting into the final runtime, the rotating tile completed 21 observed cuts with zero recovery restarts; sampled cuts were preconnected and took 250–325 ms, with no rotation errors. The migrated key, config, and database have expected owner and mode checks; the audit passes with a LAN HTTP advisory. The previous services and the previous Mosaivue release remain installed, and rollback was exercised during migration. Physical-display cut continuity awaits viewer confirmation.

On 2026-10-18, a ROCK Pi 4B+ running Debian 12 arm64 and kernel 6.1.115-8-rk2501 was installed with the GStreamer backend and `kmssink`; GDM3 was disabled to release HDMI. Rockchip `mppvideodec` and 1280×720/1920×1080 HDMI modes were detected. A real 1920×1080 camera stream advanced from 232 to 462 decoded frames with zero restarts. A local four-source H.264 RTSP smoke test at 640×360 per source and 1280×720 KMS output kept all sources LIVE for 15 seconds with zero restarts; a source replacement also completed while the others advanced. The repeatable check is `scripts/rockpi-smoke.py`. The startup fix links initial sources before setting KMS to PLAYING.

The first imported multi-camera attempt was inconclusive because one source produced zero frames in an independent low-latency GStreamer probe. The later stable-latency result is recorded below. Long-run camera capacity, boot recovery, and rotation timing remain to be tested. Physical DRM/KMS output on Pi 4 and Pi 5 remains unqualified. Run the [hardware test plan](docs/hardware-test-plan.md) before making broader device-specific capacity claims.

On 2026-10-19 UTC, the ROCK Pi 4B+ completed a second four-source KMS smoke test with two prepared source switches and zero restarts. Further tracing separated two errors that had shared the same dashboard symptom. The UniFi `rtspsrc` also reported `not-negotiated` at times. SE independently decoded 239 frames in eight seconds with FFprobe and 297 frames in ten seconds with a separate GStreamer player on the ROCK Pi, so the source itself was reachable during those probes. The full seven-stream MPP/compositor configuration remains subject to intermittent RTSP negotiation errors; long-run rotation continuity is not qualified by the short smoke results.

Additional capacity checks used saved 1280×720 layouts so the original seven-tile revision was not altered. The original seven-tile layout was reactivated for continued testing. The pre-change database backup is in the device's rollback directory. These results do not establish a stable maximum stream count.

The next seven-tile failure exposed a concrete resource leak: refreshing failed fixed or prepared camera sources left their old decoder, queue, selector pad, and RTSP connection attached to the shared pipeline. One stalled run had 11 established UniFi RTSP connections for a wall that should have eight (six fixed plus two rotation feeds), and a later run also stalled a fixed tile. Retired branches now stop on a GStreamer worker thread and are removed on the main loop after stopping. A branch-lifecycle test checks that RTSP teardown does not run in the caller and that the selector pad and pipeline elements are released. With this fix, the original wall completed 16 alternating cuts over 232 seconds with seven slots LIVE and eight RTSP connections, then both rotation feeds stopped with `rtspsrc not-negotiated`. The six fixed tiles remained LIVE, and the failed rotation did not recover despite fresh branches and normal connection count. The next recovery change selects the live placeholder while both sources are down so the input selector's running time can advance. The compositor is configured to ignore inactive pads and reserve 800 ms for dynamically attached camera sources. Sustained rotation and physical HDMI output remain under observation.

On the next run, the wall reached seven LIVE slots and three cuts, then the prepared camera reported `rtspsrc not-negotiated` while the active camera kept decoding. Fresh prepared branches continued failing to become ready. The input selector's inactive-pad synchronization was disabled so an independent live RTSP source is not held to the active source's segment. The original seven-tile wall then completed at least 18 alternating cuts over 277 seconds with all seven streams LIVE, eight established RTSP connections, and no renderer warnings or service restart. This exceeds the earlier three-cut and sixteen-cut failure points, though it does not qualify overnight stability or confirm the HDMI image without viewer inspection.

## 2026-10-19 rotation recovery follow-up

The repeatable two- and four-source local RTSP tests passed forced fresh standby replacement after replacing the rotation slot's generic URI decoder with an explicit video-only RTSP/depay/decode branch. A four-source test also passed prepared-source reset and fixed-source restart, and the two real rotation cameras completed four cuts in a separate headless pipeline. Local Python tests, frontend typecheck/build/tests, and the authenticated Chromium editor test passed.

Applying the explicit source to all seven real camera tiles caused widespread reconnects on startup. The saved release was restored, and the change was narrowed to rotating tiles; the six fixed tiles retain their original source path. That mixed wall started with seven LIVE tiles and eight RTSP connections but stopped after 40 cuts with queue `not-negotiated` errors. GStreamer's inactive selector pads had been allowed to return `NOT_LINKED` upstream while `sync-streams` was disabled. Setting `always-ok` on the placeholder, active, and prepared selector pads let the next mixed-wall run pass the 40-cut point with seven LIVE tiles, eight RTSP connections, zero stream or service restarts, and no renderer errors. This is a short qualification; the earlier 466-cut failure point and overnight duration remain untested on the new build.

The Pi rollout retained the previous release and a database backup under `/var/backups/mosaivue-rtsp-fix-20261019T133953Z`; the rollback script was exercised and updated to wait for the web service health check. Each controlled restart drained RTSP connections to zero before starting the renderer. The initial all-explicit release remains retained only as a failed test artifact, not as the active release.
