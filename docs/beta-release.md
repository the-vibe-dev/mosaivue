# Public beta candidate: v0.1.0b1

This document records what is ready to stage privately and what remains unqualified before making the repository or a release public. The planned release tag is `v0.1.0b1`; the Python package version is `0.1.0b1`.

## Tested path

- Raspberry Pi 3B+, 32-bit Raspberry Pi OS Bullseye, OMXPlayer hardware overlays, 1920×1080 HDMI output. The original installed renderer ran for over 12 days with seven LIVE tiles, 69,120 rotation cuts, and no service restart. It logged 121 playback-check restarts across its final seven days, including 61 on one fixed tile. The follow-up requires 30 seconds without a successful playback check before restarting one player. Its updated renderer reached seven LIVE tiles and 36 cuts with zero restarts in the initial post-update observation. The web service became healthy 17 seconds after its updated startup, while the renderer stayed running.
- Seven simultaneous live camera tiles at one test site, including an RTSPS stream from a UniFi system. This does not establish a general seven-stream capacity for other codecs, bitrates, or camera mixes.
- Camera import from displaycameras, admin setup, camera previews, visual layout editing, renderer selection, service restart, and rollback were exercised on that site.
- The two-camera rotation tile now prepares its next OMXPlayer offscreen and cuts using D-Bus positioning and layer controls. On the test Pi, more than 20 switches completed with zero recovery restarts; physical-display continuity still needs viewer confirmation.
- A ROCK Pi 4B+ on Debian 12 arm64 with Rockchip MPP and `kmssink` passed a 15-second, four-source local H.264 RTSP test at 1280×720. All four branches remained LIVE with zero restarts, and a source replacement succeeded while the other branches continued. One real camera also ran at 1920×1080 with increasing frames and zero restarts. This is an initial hardware smoke test, not a long-run or real-camera capacity result.
- The ROCK Pi 4B+ later ran the imported seven-tile 1920×1080 wall with its two-camera GStreamer rotation. The rotation branches stayed connected between cuts; the site viewer confirmed that both cameras appeared on HDMI. The two rotating UniFi profiles used `stable` RTSP latency. Later source errors exposed blocking recovery and a standby source that did not reconnect; both paths now reset sources without blocking the shared video loop. Longer running time remains to be tested.
- Python unit, integration, API, and renderer tests plus frontend build, tests, and Chromium checks are part of the staging gate. The dated results are in [Build verification](../BUILD-VERIFICATION.md).

## Limits to state in a public beta

- Physical output and hardware decoder performance on Raspberry Pi 4 and Pi 5 remain unqualified.
- ROCK Pi 4B+ has KMS/MPP smoke results and a real seven-tile run with viewer confirmation of both rotation cameras. An earlier approximately ten-hour run stopped switching after 466 cuts while the active rotation camera and other six tiles remained LIVE. The renderer marks repeated missed cuts as `DEGRADED` in API and dashboard health. Its video-only rotation branch passed forced fresh replacement and source recovery tests on the ROCK Pi. The mixed seven-tile wall passed 1,082 cuts over more than four hours after inactive selector pads were configured to accept standby buffers. The next overnight observation found six fixed tiles LIVE but the rotation tile STALLED after 1,799 cuts because two retired RTSP branches failed to stop. A targeted slot restart could not clear them; a drained renderer restart restored the wall after one cold-start recycle. The follow-up has a cooldown-protected whole-renderer fallback after a sustained rotation stall. The 2026-10-22 long-run recheck still found repeated rotation stalls and 11 systemd renderer restarts since deployment. A newer build selects only video before RTSP setup and passed short real-camera and seven-tile checks, but by 2026-10-26 it had recorded 33 renderer restarts and recurring `not-negotiated` errors. Single-process cold-start and overnight rotation remain unqualified. This is a ROCK Pi 4B+ result, not a Raspberry Pi 4 result.
- On 2026-10-26, the two rotating UniFi profiles were moved from RTSP 7447 to RTSPS 7441 with an app-scoped CA file and a certificate-matching local hostname. The secure feeds passed four headless cuts and an initial seven-tile wall check with two RTSPS and six RTSP connections. The first full-wall cold start failed after a 60-second drain; the successful retry needed a 120-second drain. During the next hour the wall stayed seven LIVE with no renderer restart, but logged two `not-negotiated` events and two failed rotation cuts before recovering. By the 2026-10-27 recheck it had recorded six renderer restarts from stalled rotation recovery, so the secure endpoint also failed the overnight gate. Long-run rotation and cold-start reliability remain unqualified.
- Commit `ea8bae6` fixes standby and retired queue error classification. Its first ROCK Pi startup still stalled six fixed feeds and recycled once; the next process reached seven LIVE tiles with advancing rotation and no initial errors. A long run is needed to determine whether the queue fix prevents the overnight rotation failure. The cold-start recycle remains a separate release gate.
- The 2026-10-27 cold-start follow-up spaces initial GStreamer camera launches, starts downstream queues before sources, and selects only video before RTSP setup for fixed as well as rotating feeds. A four-source audio-advertising smoke test passed, then two controlled real seven-tile starts reached all seven LIVE on their first renderer process within 22 and 27 seconds. The first start needed one fixed-tile retry; the second had no stream retry or startup error. Its next 41 rotation cuts kept all seven LIVE with no restarts, but RTSP errors and one failed cut recovered during that interval. This is evidence that the observed cold-start failure is corrected on the tested wall, while an overnight rotation run is still required before the ROCK Pi path can be called stable.
- The 2026-10-28 overnight check found one ROCK Pi renderer recycle after blocked rotation-branch teardown. The following process had about 12.4 hours of uptime, seven LIVE tiles and nearly 3,000 cuts, but logged 22 failed rotation steps and retained an extra RTSPS connection with unread data. Rotation advanced during the check; long-run recovery remains unqualified.
- The 2026-10-28 follow-up stops the downstream GStreamer queue before its RTSP source during branch retirement and recovery. It passed focused tests and a forced-fresh two-source hardware smoke test. Its first full-wall installation reached seven LIVE tiles and advancing rotation on the first renderer process, with two RTSPS plus six RTSP sessions. Overnight observation on this build remains the ROCK Pi release gate.
- An Ubuntu 24.04.5 AMD64 VM with a passed-through RTX 3060 started the same seven-tile GStreamer wall on an Xorg `ximagesink` screen. Its first process reached seven LIVE tiles, advancing frames and rotation, and measurable NVIDIA decoder use. The GPU reports no physically connected HDMI/DP display, so this is a virtual-screen result; monitor output and overnight stability are separate gates. The installer now supplies Ubuntu's separate `gstreamer1.0-x` package.
- The 2026-10-29 overnight samples showed Pi 3 seven LIVE throughout about 14 hours. ROCK Pi's rotation repeatedly stalled and two fixed feeds stayed DEGRADED without frames; Ubuntu's rotation stalled for several hours and its renderer recycled once. The fixed-feed watchdog defect was corrected, and both GStreamer appliances now trial RTSP 7447 for the two rotating profiles using the same camera paths that remained stable on Pi 3. Early checks returned seven LIVE tiles, but this does not qualify an overnight GStreamer run. Rollback copies are retained on both appliances.
- Eight hours after that trial began, Pi 3 and Ubuntu still had seven LIVE tiles in every five-minute sample, with advancing rotation and no renderer restart. ROCK Pi's six fixed tiles stayed LIVE but its rotation was STALLED in 80 of 96 samples, with persistent `not-negotiated` errors beginning 43 minutes after startup. Its cut counter continued advancing and therefore cannot establish successful displayed cuts. A ROCK Pi-only trial now skips Rockchip MPP decode for the rotation branches while retaining it for fixed tiles. A short local smoke test and first seven-tile checks passed; long-run qualification is pending.
- Later on 2026-10-29, a monitor was connected to the Ubuntu VM's passed-through RTX 3060. Xorg detected HDMI-0; assigning its 1920×1080 at 60 Hz mode made the seven-tile wall visible on the physical monitor, as confirmed by the site viewer. This qualifies physical output for this Ubuntu GPU setup. Long-run stability after the HDMI activation remains under observation.
- The ROCK Pi software-rotation trial reached 2.69 hours on one renderer process with all 30 five-minute samples at seven LIVE, a LIVE rotation tile, and 645 cuts at the direct check. The site viewer confirmed the wall and rotation appeared stable on HDMI. One fixed feed recovered from a single stream error; the rotating tile had no restarts. An overnight run is still required for ROCK Pi long-run qualification.
- The Ubuntu HDMI monitor later went to DPMS Off after Xorg's default ten-minute idle timeout, although the seven camera tiles remained LIVE. The dedicated Xorg configuration now disables the screen-saver and DPMS idle timeouts; a controlled restart verified Monitor On, active 1080p HDMI, and seven LIVE tiles. The viewer confirmed the physical signal returned. A longer post-fix soak remains pending.
- The 2026-10-30 overnight check found Pi 3 seven LIVE in all 183 samples over 15.2 hours, and ROCK Pi seven LIVE in all 208 samples over 18.1 hours with software-decoded rotation and 4,363 advancing cuts. Neither renderer recycled. Ubuntu kept HDMI active after the DPMS fix but its hardware-decoded rotation was STALLED in 91 of 175 samples and recycled once. A software-rotation trial began on Ubuntu; its overnight result remains pending. The installer now probes each available H.264, H.265, and JPEG decoder as the service account, chooses working hardware for fixed tiles and software for rotation, and saves the choices. Isolated ROCK Pi and Ubuntu tests confirmed the chosen decoders were actually loaded on a fixed and rotating synthetic RTSP tile. A clean Debian 12 installation passed; a synthetic probe does not qualify arbitrary camera profiles or a long-running wall.
- The decoder-policy build was installed through the normal source installer on ROCK Pi and Ubuntu. Both returned to seven LIVE tiles after the temporary decoder override was removed. Stream health confirmed `avdec_h264` on the rotating tile, `mppvideodec` on ROCK Pi fixed tiles, and `nvh264dec` on Ubuntu fixed tiles. Ubuntu's HDMI monitor remained On at 1080p. The installer also grants detected NVIDIA device nodes inside the renderer's systemd sandbox; a clean isolated install exercised that rule. Retained releases, install snapshots, and rollback scripts are on both test walls. Continue the overnight soak on this final installed build before publishing a beta candidate.
- The 2026-10-31 overnight check passed on Pi 3 and Ubuntu, but ROCK Pi's rotation was STALLED in 213 of 245 samples after three hours. Its six fixed tiles stayed LIVE; repeated `not-negotiated` errors kept both rotation branches from being ready while intermittent frames prevented the existing long-stall recovery from recycling the process. A manual renderer restart restored seven LIVE tiles. Commit `25baf07` adds a cooldown-limited recycle after two minutes of persistent rotation negotiation errors on an unhealthy tile and was installed with rollback retained. This is a recovery improvement; ROCK Pi long-run rotation remains unqualified until another overnight run shows its actual behavior.
- The 2026-11-01 follow-up found Pi 3 and Ubuntu seven LIVE in every sample over about 14 hours, with no restart; Ubuntu HDMI remained On. ROCK Pi was seven LIVE in 162 of 163 samples. Its rotation hit `not-negotiated` at 16:12:55 UTC, then the new guard recycled the renderer at 16:14:56. The next process stayed seven LIVE for about 9.9 hours with advancing rotation and no further failed cut. The guard prevents an all-night stall, but one automatic wall interruption means ROCK Pi still has not met a zero-recycle overnight qualification gate.
- A new ROCK-only trial normalizes the two rotation feeds to identical raw caps before the selector. The real feeds are both H.264/30 fps but differ in size (1024×576 and 640×360); the tested normalization target is 640×360 I420 at 15 fps. Mixed-resolution local RTSP tests passed ten cuts and then two more, with no restart and equal branch caps. The real seven-tile wall came back LIVE with matching active, prepared, and selector caps, and its five-minute sampler now records them. The underlying fault is not yet closed; evaluate the overnight samples and any new caps diagnostics before a ROCK Pi beta claim.
- Legacy OMXPlayer lacks exact crop, opacity, label overlay, snapshot, and native pixel-size behavior. It uses letterbox for the `native` aspect choice.
- OMXPlayer `preconnect=next` uses one bounded extra decoder for sequential or reverse groups. Random and weighted groups prepare at switch time. There is no `all` preload mode.
- LAN HTTP, local access to the `mosaivue` service account, and legacy OMXPlayer process arguments are trust boundaries. See [security design](security.md).
- The beta has no universal stream-count or latency guarantee. Record camera codec, resolution, frame rate, decoder, sink, CPU, and temperature for each hardware claim.

## Private staging and publication gate

1. Keep the staging repository private while reviewing source, screenshots, license inventory, generated OpenAPI, and built archives for site credentials or private deployment files.
2. Confirm the Python package version, Git tag, changelog, source archive name, and GitHub prerelease flag agree.
3. Resolve the GitHub Actions account billing/spending-limit error, then run CI. The checksum-verifying bootstrap, clean Debian 12 source install, rollback failure injection, `.deb` install/removal, frontend build/tests, release checker, and ROCK Pi service activation have passed locally or on the appliance. Repeat the hardware matrix before broader platform claims.
4. Repeat the ROCK Pi cold start and overnight rotation on the staged build. The queue-first teardown build passed its first full-wall start; an overnight run must confirm that rotation recovers without a prolonged black tile or repeated renderer recycle.
5. Review the [security policy](../SECURITY.md) and [third-party notices](../THIRD_PARTY_NOTICES.md), especially the external OMXPlayer and FFmpeg dependencies.
6. Publish a public repository or prerelease only after the staged commit and artifacts have been reviewed. The release workflow creates a prerelease for beta tags; staging a branch does not create a tag or release.

The new Mosaivue repository is staged privately first. Its CI must pass before public publication; local checks and Pi results are recorded in [Build verification](../BUILD-VERIFICATION.md).

## Feedback to request from beta users

Ask for board model, OS and kernel, display mode, renderer backend, codec/profile mix, `mosaivue doctor --json`, and sanitized logs. Never request camera passwords, complete backups, or raw RTSP URLs in a public issue.
