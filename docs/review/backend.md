# Mosaivue backend review and implemented corrections

## Scope and result

Reviewed API authentication, CRUD and events, the database model and transaction boundaries, camera/stream identity, layout validation, configuration backup/restore, diagnostics, and stream probing. Changes were implemented in the shared source tree without a database schema migration. Engineering priorities below describe user impact; they are not CVSS scores or a claim of a complete penetration test.

**Final focused verification: 70 tests passed**, including **52 new regression cases** beyond the original 18 cases in these selected files. Runtime verification used Python 3.12, SQLAlchemy/SQLite, FastAPI TestClient, real AES-GCM encryption/decryption, real ZIP archives, concurrent threads and separate database connections. GStreamer discovery and transport tests used controlled test objects; they do not qualify physical cameras, codecs, first-frame latency or HDMI output.

## Restore behavior and operational choices

API import/restore commits the configuration before asking the renderer to apply the resulting active wall. The response separates `renderer_applied` from configuration success and provides `renderer_warning` if the daemon cannot apply it or no active layout is selected. This avoids reporting a failed restore after configuration was successfully saved. The frontend displays that warning persistently.

A sanitized **merge** keeps existing credentials. A sanitized **replacement** has no old credential to preserve; cameras that require one need it re-entered. Merge preserves the existing active layout rather than unexpectedly changing the displayed wall. Historical revisions may refer to cameras deleted in the past; they are preserved as history, while current layouts and rotation groups must have valid references. Trying to restore an unusable historical revision returns a validation response.

The CLI restore path remains a database/configuration operation; apply a layout or restart the renderer afterward. The root review adds an explicit CLI instruction for this limitation.

Installer coordination: when `/etc/mosaivue` is protected from service-user directory writes, the one-time token is consumed by overwriting and flushing its existing group-writable inode if unlink is denied. Empty token files do not authorize setup and are reported as unavailable. Directory diagnostics now flag group-writable configuration directories. Root-owned metadata protection and installer changes are covered by the separate packaging review.

## Remaining gaps and recommended next work

1. **Apply camera edits to an already-running fixed wall predictably.** CRUD persists configuration, but existing renderer specifications retain the old URL/profile until layout reapplication. Rotation edits partly take effect on the next transition; interval/preconnect changes also need reapplication. An explicit apply action and pending-change indication are preferable to silently exiting a user's focus view on every save. A daemon-side revision/reload contract could support later automatic updates.
2. **Keep backup scope precise.** These are credential-inclusive configuration backups, not full appliance recovery images. They do not include web users/sessions, `/etc/mosaivue/config.json`, renderer-backend override, custom TLS CA files, OS packages or systemd customizations. A versioned appliance-settings section with preview and a restore rehearsal would close this gap.
3. **Account and automation access management is incomplete.** The model has an admin flag, but there is no complete account/role management product surface, read-only/operator role, scoped revocable service token or independently managed integration credential. Do not market the current interface as multi-user RBAC.
4. **Audit history is not implemented.** `AuditLog` exists as a model but normal API mutations do not populate an operator-facing audit trail. Add actor/resource/action logging with explicit secret exclusion and bounded retention before team/shared-wall deployment.
5. **Full RTSP URI confidentiality is narrower than the credential claim.** Usernames/passwords are separated and encrypted. Bearer tokens embedded in camera-specific URL paths, including opaque vendor stream paths, remain part of the stored URL and exported configuration. Generic redaction cannot reliably identify them. Encrypt the full URI or model credential-bearing URL components explicitly before promising encryption of every stream secret.
6. **Settings validation needs its own typed contract.** `Settings.from_mapping` accepts values directly into a dataclass. Incorrect enum/type values, including string booleans, are not consistently rejected. This should be addressed with compatibility tests for existing configuration files.
7. **Real hardware qualification remains essential.** Discovery-result correctness and transport propagation are tested as contracts. Real authentication failures, TLS trust, UDP behavior, codec availability, actual decoded first-frame time, CPU usage during concurrent previews, camera disconnect/reconnect and long-duration HDMI operation still need representative appliances/cameras.
8. **Preview work has no explicit appliance-wide concurrency budget.** Each capture is bounded by timeouts, but many authenticated preview requests can still compete for CPU and decoder resources. A small shared capture queue/cache would protect lower-power Pis while improving thumbnail responsiveness.
