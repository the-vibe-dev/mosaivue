# Competitor comparison and product roadmap

Reviewed November 12, 2026. This comparison uses official project repositories and vendor documentation. A documented feature is evidence of what a project offers or claims; it is not independent performance or reliability verification. Pricing, camera-count promises, and unsupported hardware comparisons are deliberately excluded.

## Recommended product position

Mosaivue should concentrate on being an approachable, local camera-wall appliance for reused Raspberry Pi and Linux hardware. Its useful combination is a visual layout editor, reusable camera profiles, independent rotating tiles, phone control, encrypted configuration, and recovery diagnostics. The review build improves that existing foundation and adds an ONVIF Media1 import workflow for a known device endpoint. That is useful setup automation, but it is not automatic network discovery or full ONVIF control.

The strongest next investments are dependable installation/recovery, easier camera onboarding, accurate capability reporting, and actual multi-display support. These directly improve the job the product already performs. Rebuilding the storage, event search, and detection stack of a full NVR would create a much larger product with different resource and maintenance requirements.

## Gaps reduced by this review build

The changes address several practical reasons users might choose another viewer: loss of substream selection during rotation, interference between two tiles using one group, failed layout updates damaging the current wall, incorrect overnight scheduling, controls that did not match OMX behavior, and limited setup visibility. The new schedule interface, stronger camera/profile editing, ONVIF endpoint import, and more useful remote controls improve everyday operation.

The implementation also makes performance tuning explicit: `MOSAIVUE_OUTPUT_FPS` controls GStreamer's compositor rate while preserving the original five-FPS default. A setting of 30 does not prove a particular device can deliver 30 frames per second. Physical measurements remain necessary, especially with multiple decoders and independently rotating sources.

Treat those corrections as improvements to the reviewed source build, not as blanket parity with every product above. The accompanying runtime and backend reports specify which results were verified by automated contracts and which require actual cameras, operating systems, and displays.

## Prioritized next roadmap

### P0 — prove the revised appliance is dependable

**Run a reproducible hardware acceptance suite.** Exercise the existing Pi 3B+/OMX, ROCK Pi/GStreamer, and Ubuntu setups with cold boot, mixed aspect ratios, unavailable cameras, multiple rotation slots, repeated layout changes, and prolonged operation. Record source codecs/resolutions, selected decoder, output rate, memory/CPU, failed switches, recovery time, and fixed-tile continuity. Publish exact tested combinations rather than a universal stream count.

**Finish capability-aware controls.** Hide or explain controls a backend cannot render. Current remaining examples include OMX text/manual-crop behavior, display portrait/output targeting, synchronized rotation, and the placeholder failure policy. Acceptance means every visible control produces a measured effect or clearly explains its limitation. This matters more than adding additional options to the settings schema.

**Exercise actual upgrade and recovery.** Test installing from the ZIP/source archive, restarting after a power loss, restoring sanitized and encrypted backups, and reverting a failed update. The acceptance record should include a retained camera/profile association and a recoverable previous version. The artifact must be useful on a clean host, not only inside a developer checkout.

### P1 — close the strongest direct display gaps

**Implement output targeting and portrait mode.** Model a physical output separately from a layout; map it to the actual DRM/Wayland connector; persist configuration across reboots and disconnection. Add independent layouts and playlists per monitor. Start with one verified backend/platform pair, then expand. Acceptance requires two different visible walls and a measured portrait layout, not an extra database column.

**Expand onboarding in bounded steps.** Build on the endpoint importer with explicit local WS-Discovery and selectable discovered devices, followed by Media2 compatibility and PTZ preset control. Keep credential storage and error reporting consistent with manual camera entry. Test authentication variants, unavailable devices, duplicate imports, and profile changes against real cameras before broad compatibility claims.

**Add display playlists and image tiles.** Whole-layout cycling addresses a different use case from per-tile rotation. Allow a playlist per display, dwell time, pause/next/previous, and schedule selection. Add locally cached images with controlled refresh for status boards. Preserve fixed layout geometry unless the user chooses automatic reflow.

### P2 — improve management and integrations

**Optional browser live viewing.** Reuse an explicitly enabled local restreamer for MSE/WebRTC, expose supported codecs clearly, and open streams only while needed. Confirm that phone viewing does not starve HDMI decoding or unnecessarily multiply camera connections. Treat audio/PTZ as separate capability checks.

**Operational visibility.** Add bounded historical health, metrics export, camera outage alerts, and a clear distinction between observed video frames and player-process health. An operator should be able to answer which tile failed, when it last worked, and what recovery was attempted without collecting raw logs manually.

**Managed deployments.** After one appliance is dependable, add operator/viewer roles, narrowly scoped automation credentials, and optional multi-appliance configuration/health management. Preserve local operation when that controller is offline.

### Keep outside the immediate release

Full NVR recording, analytics, event search, cloud retention, and billing should remain integrations or separate projects unless user demand changes the product goal. The recommendation is based on implementation scope and Mosaivue's current architecture, not on an assumption that those capabilities lack value. A dependable camera-wall appliance has a clear purpose even when an existing NVR supplies the feeds.
